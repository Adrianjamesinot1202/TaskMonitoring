GUIDELINES FOR CODING

==============================================================================
STRICT DOCUMENTATION COMPLIANCE
==============================================================================

Before reviewing, creating, or modifying a module, check and strictly follow the
applicable project documentation. Do not change, enhance, reinterpret, or extend
a documented implementation pattern unless the current task or a senior
instruction explicitly approves the deviation.

Required documents to check:
- Full-Stack_Coding_Standards_and_Development_Guidelines.docx
- JavaScript_Task_Module_Coding_Standard.docx
- JS Limitless Developer Documentation (1).docx
- PHP Limitless Developer Documentation (1).docx
- Dynamic Datalist.docx when implementing or reviewing a datalist

When a documented global function or implementation pattern applies, follow its
documented parameters, structure, and usage exactly. Do not substitute a custom
implementation merely to add behavior that was not requested.

If the current task or a senior instruction conflicts with a document, follow
the current task or senior instruction and clearly identify the approved
deviation.

This guide is the project coding standard for PHP modules, AJAX components, route.php files, JavaScript task files, uploads, modals, and server-rendered UI.

Main goal:
Write simple, readable, secure, review-friendly code that follows the existing Limitless/E2E project structure.

Reference documents:
- PHP Limitless Developer Documentation (1).docx
- JS Limitless Developer Documentation (1).docx
- Full-Stack_Coding_Standards_and_Development_Guidelines.docx
- JavaScript_Task_Module_Coding_Standard.docx

If a current senior instruction conflicts with this guide, follow the senior instruction for that task, then update this guide afterward so the rule stays clear.

==============================================================================
1. CORE RULES
==============================================================================

- Keep code simple, readable, consistent, secure, and maintainable.
- Follow the structure already used by nearby working modules.
- Do not over-abstract simple logic.
- Do not create one-use helper functions, wrapper functions, wrapper files, or extra shared folders for small tasks.
- Use existing global helpers directly before creating any new function.
- Do not wrap global helpers just to rename them.
- Keep SQL visible and easy to review.
- Keep JavaScript focused on UI behavior, event binding, AJAX calls, modal control, and container refresh.
- Keep PHP responsible for database queries, validation, business rules, and final security checks.
- Preserve existing selectors, routes, form names, and backend calls unless the task requires changing them.
- Do not rewrite unrelated working code just to apply a standard.
- Do not leave temporary debug output or test code.
- Do not store passwords, tokens, database credentials, or secrets in this guide.

Examples of helpers that must be used directly:

```php
sanitize_input()
normalize_html_entities()
json_msg_response()
exception_handler()
auditTrail()
auditDiff()
upload_multiple_files()
prepare_file_for_preview()
get_attachment_file_paths()
delete_attachment()
```

```javascript
bindEvent()
handleAjaxResponse()
handleAjaxError()
showConfirm()
loading()
startProcessLoader()
endProcessLoader()
createMultiFileUploadSection()
buildFilesFormData()
viewSecureFileInModal()
viewSecureFileInLine()
```

Avoid this:

```php
function birthregistry_entry_html($value) {
    return normalize_html_entities((string)$value);
}
```

Use this directly:

```php
<?php echo normalize_html_entities($row['RegistrantFirstName'] ?? ''); ?>
```

==============================================================================
2. FOLDER RESPONSIBILITIES
==============================================================================

main.php / *-main.php
- Static page layout.
- Static page header, search fields, filters, table headers, and placeholder containers when only the body/list refreshes.
- Static modals/offcanvas containers when the modal is part of the page shell.
- Static delete confirmation modal only if the module standard explicitly keeps it there.
- Script imports.
- No module CRUD queries.
- No save/update/delete logic.
- No inline JavaScript event attributes.
- Do not directly include component files unless explicitly approved.

components/
- Server-rendered HTML fragments.
- Summary tables, table bodies, cards, rows, detail panes, tab content, and AJAX-loaded entry/modal content.
- Read-only display queries.
- Option/datalist/select list rendering when options come from the database.
- Use class names and data-* attributes for JS actions.
- No database insert, update, or delete.
- No inline JavaScript event attributes.

actions/
- Save, update, delete, and focused request handlers.
- Sanitize and validate request data.
- Validate related records and business rules.
- Execute database writes using prepared statements and transactions.
- Handle upload processing when needed.
- Prepare audit data and call auditTrail() when required.
- Return JSON using json_msg_response().
- No HTML UI output.

script/
- Module variables.
- bindEvent() declarations.
- AJAX calls.
- Summary/detail/component loading.
- Modal open/reset/fill logic.
- Form submit logic.
- Confirmation routing.
- Loading states.
- No SQL.
- No large HTML layout building.

route.php
- Route registration only.
- No business logic.
- No database queries.
- Must contain the module config block when used by the router.

shared/
- Do not create for normal registry modules.
- Use only for API modules or explicitly approved reusable infrastructure.

3. NAMING AND STYLE RULES
==============================================================================

Use clear names that show ownership and purpose.

Component suffixes:
- *_summary.php = list/table/card summary.
- *_details.php = detail pane, tab content, single-record detail.
- *_entry.php = entry form/modal/offcanvas content.
- *_options.php = option/datalist/select HTML or JSON source.

Action prefixes:
- save_*.php
- update_*.php
- delete_*.php
- get_*.php

JavaScript function names:
- Use the module/task prefix first.
- Use names that describe the registry/entity and action.
- Follow the existing module naming style before introducing a new casing style.
- Current registry modules commonly use snake_case for JS functions and route keys. Keep that style unless a full rename is approved.

Preferred:

```javascript
expenseclass_summary()
expenseclass_add()
expenseclass_update()
expenseclass_delete()
barangay_official_save()
barangay_official_delete()
birthregistry_summary()
birthregistry_open_entry()
```

Avoid:

```javascript
save()
update()
deleteRecord()
load()
getData()
handle()
process()
```

General naming rules:
- Meaningful ownership is more important than short names.
- Avoid unclear names such as data, value, thing, temp, test, id1, process(), and handle().
- Use camelCase only when the existing file/module already uses camelCase.
- Do not mix naming styles inside the same file without a reason.

PHP syntax rules:
- Use standard PHP echo syntax.
- Do not use short echo tags.
- Use standard curly braces for if/else, loops, try/catch, and functions.
- Do not use alternative colon syntax for control structures.
- Keep indentation and spacing clean.

Preferred:

```php
<?php echo normalize_html_entities($employeeName ?? ''); ?>

if ($isActive) {
    echo 'Active';
} else {
    echo 'Inactive';
}
```

Avoid:

```php
<?= $employeeName ?>

<?php if ($isActive): ?>
    Active
<?php endif; ?>
```

5. INPUT SANITIZING AND OUTPUT NORMALIZATION
==============================================================================

Use sanitize_input() for incoming external data:
- $_POST
- $_GET
- JSON request data
- Uploaded file metadata when applicable
- User-generated input

sanitize_input() can process strings and arrays.

Example:

```php
$search = sanitize_input($_POST['search'] ?? '');
$recordID = (int)sanitize_input($_POST['RecordID'] ?? 0);
```

Use normalize_html_entities() for database/external values being displayed or returned:
- Direct HTML display: use default raw = false.
- JSON/API/AJAX/JavaScript processing: use raw = true.

Direct HTML display:

```php
<?php echo normalize_html_entities($row['ExpenseClassName'] ?? ''); ?>
```

JSON/API value:

```php
$name = normalize_html_entities($row['ExpenseClassName'] ?? '', true);
```

Rules:
- Do not create wrapper functions for normalize_html_entities().
- Do not use htmlspecialchars() directly in module components unless there is a documented reason.
- Do not confuse sanitize_input() and normalize_html_entities().
- sanitize_input() protects incoming request data.
- normalize_html_entities() prepares stored/external text for output.

==============================================================================
6. PHP ACTION STANDARD
==============================================================================

For save/update/delete actions:
- Use POST.
- Use prepared statements.
- Use try/catch.
- Use $conn->beginTransaction() inside try.
- Validate input and business rules before writing.
- Validate related records before insert/update/delete.
- Use UserException for user/business-rule validation errors.
- Use exception_handler($e, $conn) in catch.
- Return JSON using json_msg_response().
- Do not manually echo JSON.
- Do not use error_log() in final module files.
- Do not use SELECT *.
- Do not use fetchAll().
- Pass $conn to json_msg_response() when rollback may be needed.

Standard action shape:

```php
<?php
require_once $_SERVER['DOCUMENT_ROOT'] . "/check_session.php";
require_once $_SERVER['DOCUMENT_ROOT'] . "/connection.php";
require_once $_SERVER['DOCUMENT_ROOT'] . "/functions.php";

header('Content-Type: application/json; charset=utf-8');

$recordID = (int)sanitize_input($_POST['RecordID'] ?? 0);

try {
    $conn->beginTransaction();

    // Validate request data.
    // Validate related records.
    // Insert, update, or delete using prepared statements.
    // Prepare audit data before commit.

    $conn->commit();

    auditTrail($conn, $auditData);

    json_msg_response(200, 'success', 'Record saved successfully.', $conn, [
        'recordID' => $recordID
    ]);
} catch (Throwable $e) {
    exception_handler($e, $conn);
}
```

Delete action rule:
- First fetch the record that will be deleted.
- If it no longer exists, return a user/business warning.
- Use the fetched data for audit.
- Then delete the record.

This protects stale screens where another user already deleted the same record.

==============================================================================
7. TRANSACTION AND AUDIT TRAIL RULES
==============================================================================

Write actions must use transactions:
- CREATE: beginTransaction / commit / rollback through exception handling.
- UPDATE: beginTransaction / commit / rollback through exception handling.
- DELETE: beginTransaction / commit / rollback through exception handling.

SELECT transactions are optional unless transactional consistency is required.

Audit trail order:
1. Start transaction inside try.
2. Validate request data.
3. Validate related records.
4. Get old data if this is update/delete.
5. Run insert/update/delete.
6. Prepare $auditData before commit.
7. Call $conn->commit();
8. Immediately call auditTrail($conn, $auditData);
9. Return json_msg_response().

Create audit:

```php
$auditData = [
    'UserID' => $_SESSION['UserID'],
    'Module' => 'Expense Class Registry',
    'Action' => 'Create',
    'ReferenceNo' => $expenseClassCode,
    'Description' => 'Created expense class.',
    'Data' => $newData
];
```

Update audit:

```php
$auditData = [
    'UserID' => $_SESSION['UserID'],
    'Module' => 'Expense Class Registry',
    'Action' => 'Update',
    'ReferenceNo' => $expenseClassCode,
    'Description' => 'Updated expense class.',
    'Data' => auditDiff($oldData, $newData)
];
```

Delete audit:

```php
$auditData = [
    'UserID' => $_SESSION['UserID'],
    'Module' => 'Expense Class Registry',
    'Action' => 'Delete',
    'ReferenceNo' => $expenseClassCode,
    'Description' => 'Deleted expense class.',
    'Data' => $oldData
];
```

Audit rules:
- For update, use auditDiff() when old and new data are available.
- For delete, retrieve the record before deletion.
- Do not store passwords, tokens, or sensitive data in audit.
- Do not skip audit after commit unless the current task explicitly says audit is not yet included.

==============================================================================
8. VALIDATION AND DUPLICATE RULES
==============================================================================

Backend validation is always the final guard.

General rules:
- Validate required values.
- Validate allowed values.
- Validate IDs and foreign keys.
- Validate duplicate code/name rules.
- Validate business rules in PHP even if the UI also helps prevent mistakes.
- HTML required/min/max/maxlength attributes are user convenience only. They do not replace PHP validation.

Duplicate checks:
- Use SELECT 1 ... LIMIT 1 for existence checks.
- Do not use COUNT(*) unless the requirement is to return an actual count.
- On update, exclude the current record from the duplicate check.

Add duplicate example:

```php
$stmtDuplicate = $conn->prepare("
    SELECT 1
    FROM tblexpense_class
    WHERE ExpenseClassCode = ?
        OR ExpenseClassName = ?
    LIMIT 1
");
$stmtDuplicate->execute([$expenseClassCode, $expenseClassName]);

if ($stmtDuplicate->fetchColumn()) {
    throw new UserException('Expense class code or name already exists.');
}
```

Update duplicate example:

```php
$stmtDuplicate = $conn->prepare("
    SELECT 1
    FROM tblexpense_class
    WHERE (ExpenseClassCode = ? OR ExpenseClassName = ?)
        AND ExpenseClassCode <> ?
    LIMIT 1
");
$stmtDuplicate->execute([$expenseClassCode, $expenseClassName, $currentCode]);
```

Assignment/tagging tables:
- Prevent duplicate active person/name under the same parent record.
- Prevent duplicate active position/type under the same parent record.
- Allow inactive/history records when business rules allow history.
- On update, exclude the current record ID from duplicate checks.
- Frontend may hide already-used options, but PHP must still validate.

Date validation:
- Validate date format in PHP.
- If there is a start and end date, end date must not be earlier than start date.
- If a date cannot be in the future, validate it in PHP and set the frontend max attribute when useful.
- Do not loop date values from the database just to reformat them. Format once per fetched row.

==============================================================================
9. FILE UPLOAD RULES
==============================================================================

Use upload_multiple_files() for server-side upload processing when available.

Important split:
- JavaScript upload helpers manage the upload UI only.
- PHP upload helpers perform the real validation, file storage, and database attachment updates.

Backend rules:
- Validate file rules in PHP.
- Use upload_multiple_files() instead of duplicating folder creation and file moving logic.
- Do not leave upload debug echoes or debug files.
- On update, call upload_multiple_files() only when a new file was selected or existing files changed.
- If no file changed, keep the existing filename/file record and skip upload logic.
- If upload fails, return json_msg_response(..., $conn) before commit so the transaction rolls back.
- When upload rules are only needed inside an upload condition, declare the upload parameter array inside that same if block.
- Keep accept_extensions close to the upload_multiple_files() call so reviewers do not need to scroll up to verify allowed file types.

upload_multiple_files() structure:

```php
$other_requirements = [];

$uploadResult = upload_multiple_files(
    $conn,
    (int)($_SESSION['UserID'] ?? 0),
    $_FILES['DOCUMENT_FILE'],
    $_POST['DOCUMENT_FILE_existing'] ?? [],
    $moduleCode,
    $moduleNo,
    $moduleSub,
    1,
    '5MB',
    $other_requirements
);

if (!($uploadResult['success'] ?? false)) {
    json_msg_response(400, 'error', $uploadResult['msg'] ?? 'Upload failed.', $conn);
}
```

Custom accepted extension rule:
- Use accept_extensions when the task allows only specific file types.
- Keep the accepted extension list strictly based on the task requirement.
- Use an empty array when no custom extension restriction is required.
- Prefer declaring the accepted-extension parameter inside the upload if block when the upload is conditional.

```php
if ($hasBirthCertificateFile) {
    $other_requirements = [
        'accept_extensions' => [
            'pdf'
        ]
    ];

    $uploadResult = upload_multiple_files(
        $conn,
        (int)($_SESSION['UserID'] ?? 0),
        $_FILES['BIRTH_CERTIFICATE_FILE'],
        [],
        'BIRTH_REGISTRY',
        $registryNo,
        'BIRTH_CERT',
        1,
        '5MB',
        $other_requirements
    );
}
```

AttachmentID-based upload pattern:
- Use this pattern when the main table stores an AttachmentID column.
- Insert or fetch the main record first.
- For add/save, pass an empty attachment_id value.
- For update, pass the current record's AttachmentID.
- Store the returned attachment_id back to the main table.
- Do not build direct /attachments/uploads paths when AttachmentID is available.

Insert attachment pattern:
- Use this after the main record has been inserted and the module number/reference is already available.
- Declare $otherRequirements near the upload call.
- Pass attachment_id as an empty array for new attachments.
- Save the returned attachment_id back to the parent table.

```php
$otherRequirements = [
    'attachment_id' => [],
    'accept_extensions' => [
        'jpg',
        'jpeg',
        'png'
    ]
];

$attachmentID = null;

if ($hasLogoUpload) {
    $uploadResult = upload_multiple_files(
        $conn,
        (int)($_SESSION['UserID'] ?? 0),
        $logoFiles,
        [],
        'BRGY_UPLOADS',
        $barangayCode,
        'BRGY_LOGO',
        1,
        '100KB',
        $otherRequirements
    );

    if (!($uploadResult['success'] ?? false)) {
        json_msg_response(400, 'error', $uploadResult['msg'] ?? 'Unable to upload barangay logo.', $conn);
    }

    $attachmentID = $uploadResult['attachment_id'] ?? null;
}

if ($attachmentID !== null) {
    $stmtLogo = $conn->prepare("
        UPDATE `tblbarangay`
        SET `AttachmentID` = ?
        WHERE `BarangyID` = ?
    ");
    $stmtLogo->execute([
        $attachmentID,
        $barangayID
    ]);
}
```

View attachment pattern:
- Use get_attachment_file_paths() to get the files connected to the AttachmentID.
- Use prepare_file_for_preview() to get a safe temporary public URL.
- Use a default preview when the record has no attachment.
- Always escape src and alt output using normalize_html_entities().

```php
$logoDefaultPath = ['/assets/logo/no-logo.png'];
$logoDefaultPreview = prepare_file_for_preview($logoDefaultPath);
$logoDefault = $logoDefaultPreview['data'][0]['public_url'] ?? '';

while ($stmtBarangay && ($barangay = $stmtBarangay->fetch(PDO::FETCH_ASSOC))) {
    $attachmentID = $barangay['AttachmentID'] ?? null;
    $logo = $logoDefault;
    $logoAlt = '';

    if (!empty($attachmentID)) {
        $filepath = get_attachment_file_paths($conn, $attachmentID);

        if (!empty($filepath)) {
            $filePreview = prepare_file_for_preview($filepath);

            if (($filePreview['success'] ?? false) === false) {
                $logo = '';
                $logoAlt = $filePreview['message'] ?? 'Unable to load attachment.';
            } else {
                $logo = $filePreview['data'][0]['public_url'] ?? $logoDefault;
            }
        }
    }
    ?>
    <img
        alt="<?php echo normalize_html_entities($logoAlt); ?>"
        src="<?php echo normalize_html_entities($logo); ?>"
    >
    <?php
}
```

Update attachment pattern:
- Fetch the current parent record first.
- Get the current AttachmentID from the parent record.
- Pass the current AttachmentID through attachment_id.
- If a new attachment is uploaded, save the returned attachment_id back to the parent table.

```php
$attachmentID = $current['AttachmentID'] ?? null;

$otherRequirements = [
    'attachment_id' => $attachmentID,
    'accept_extensions' => [
        'jpg',
        'jpeg',
        'png'
    ]
];

if ($hasLogoUpload) {
    $uploadResult = upload_multiple_files(
        $conn,
        (int)($_SESSION['UserID'] ?? 0),
        $logoFiles,
        [],
        'BRGY_UPLOADS',
        $barangayCode,
        'BRGY_LOGO',
        1,
        '100KB',
        $otherRequirements
    );

    if (!($uploadResult['success'] ?? false)) {
        json_msg_response(400, 'error', $uploadResult['msg'] ?? 'Unable to upload barangay logo.', $conn);
    }

    $attachmentID = $uploadResult['attachment_id'] ?? $attachmentID;
}

if ($attachmentID !== null) {
    $stmtLogo = $conn->prepare("
        UPDATE `tblbarangay`
        SET `AttachmentID` = ?
        WHERE `BarangyID` = ?
    ");
    $stmtLogo->execute([
        $attachmentID,
        $barangayID
    ]);
}
```

Multiple attachment group pattern:
- One AttachmentID can represent one attachment group.
- Multiple uploaded files are stored under that one AttachmentID.
- The parent table stores only the AttachmentID, not one column per file.
- Use the max file limit parameter to control how many files the group accepts.

```php
$proofUploadResult = upload_multiple_files(
    $conn,
    (int)($_SESSION['UserID'] ?? 0),
    $proofFiles,
    [],
    'ENVIRONMENTAL_COMPLAINT',
    (string)$environmentalComplaintID,
    'SUPPORTING_PROOF',
    5,
    '5MB',
    $otherRequirements
);
```

AttachmentID delete pattern:
- Fetch the current parent record first.
- Get the current AttachmentID before deleting.
- Use delete_attachment() instead of manually deleting files or direct upload folders.
- Use $deleteFiles when reading delete_attachment() errors.

```php
if (!empty($current['AttachmentID'])) {
    $deleteFiles = delete_attachment($conn, $current['AttachmentID']);

    if (($deleteFiles['success'] ?? false) === false) {
        throw new UserException($deleteFiles['msg'] ?? $deleteFiles['message'] ?? 'Unable to remove attachment.');
    }
}
```

Upload + transaction order:
1. Run database insert/update first when the upload needs a document number/reference.
2. Call upload_multiple_files() before commit.
3. If upload fails, return json_msg_response(..., $conn).
4. Commit only after upload succeeds.
5. Call auditTrail() after commit.
6. Return success JSON.

Recommended upload path structure:

```txt
{moduleCode}
> {moduleNo}
> > {moduleSub}
```

JavaScript upload UI:
- Use createMultiFileUploadSection() and buildFilesFormData() for documented multi-file upload UI.
- The getter returned by createMultiFileUploadSection() should be passed to buildFilesFormData().
- If a normal file input is enough and approved, FormData may be used directly.
- Do not directly expose secure file paths in JS.

File preview rules:
- Use prepare_file_for_preview() for PHP/backend file-preview preparation.
- Do not manually stream module files with readfile(), direct PDF/image headers, ob_start(), or ob_end_clean() unless a senior specifically approves that pattern.
- Do not expose direct attachments/uploads paths to JavaScript or HTML.
- For module views that use the global file viewer, render only the preview container and safe data attributes in the PHP component, then call viewSecureFileInLine() or viewSecureFileInModal() from the module JS.
- Do not create custom module-specific preview renderers in JavaScript.
- The global secure viewer action/helper is responsible for calling prepare_file_for_preview() and returning the temporary public URL.
- Match viewer parameters to the upload structure exactly:
  - documentcode / ModuleCode = upload module code
  - documentno / ModuleNo = upload document or record number
  - extrafolder / ModuleSub = upload module subfolder
  - safefile / ModuleFiles[].name = stored safe filename
- prepare_file_for_preview() returns a result array; the caller decides how to return the success/error response.
- Local preview preparation copies the validated file into /attachments/public_temp and returns a temporary public URL.
- Validate filenames with basename/path traversal checks and rely on prepare_file_for_preview() for local path validation.

==============================================================================
10. SQL AND PDO RULES
==============================================================================

- Use PDO.
- Use prepared statements.
- Use POST for all CRUD requests.
- Do not directly concatenate user input into SQL.
- Do not prefix table names with a database name.
- Use tblname only, not database_name.tblname.
- Do not use SELECT *.
- Select only the columns needed.
- Do not use COUNT(*) unless the requirement is to count records.
- Do not use fetchAll().
- Keep SQL simple, readable, and close to the requirement.
- Avoid unnecessarily complex SQL.
- If the same SQL statement must run multiple times with different values, prepare once and execute multiple times.
- If two lists/tabs come from the same table and same context, avoid duplicate queries when possible.

Search pattern:
- Use CONCAT_WS with one LIKE parameter.
- Empty search becomes %% and should still select all rows.

Example:

```php
$search = sanitize_input($_POST['search'] ?? '');
$like = '%' . $search . '%';

$stmt = $conn->prepare("
    SELECT RecordID, RecordCode, RecordName
    FROM tblsample
    WHERE CONCAT_WS(', ', RecordCode, RecordName) LIKE ?
    ORDER BY RecordName ASC
");
$stmt->execute([$like]);
```

Avoid:

```php
WHERE RecordCode LIKE ?
    OR RecordName LIKE ?
    OR Description LIKE ?
```

==============================================================================
11. DIRECT DATABASE DISPLAY LOOP RULES
==============================================================================

For display components, render database rows directly with while.

Preferred:

```php
while ($row = $stmt->fetch(PDO::FETCH_ASSOC)) {
    ?>
    <tr>
        <td><?php echo normalize_html_entities($row['RecordCode'] ?? ''); ?></td>
        <td><?php echo normalize_html_entities($row['RecordName'] ?? ''); ?></td>
    </tr>
    <?php
}
```

Avoid:

```php
$rows = [];

while ($row = $stmt->fetch(PDO::FETCH_ASSOC)) {
    $rows[] = $row;
}

foreach ($rows as $row) {
    // render row
}
```

foreach is allowed for non-database arrays:
- Static option arrays.
- Uploaded file arrays.
- POST array values.
- Small configuration arrays.
- Lookup maps already created for a real purpose.
- Old/new data arrays for auditDiff().

Arrays are allowed only when they serve a real purpose:
- Grouping rows.
- Checklist state.
- Totals that must be calculated before display.
- Reusing a small static configuration.

Do not convert a simple database result to an array just to loop it again.

==============================================================================
12. COMPONENT RULES
==============================================================================

- Components render server-side HTML.
- Components can return JSON only for option/detail AJAX modes when needed.
- Components must not write to the database.
- Components must not contain save/update/delete logic.
- Components must not contain inline JavaScript events.
- For JS-triggered actions, output class names and data-* attributes only.
- Components should query near the top, then render below.
- Use direct while fetch loops for display rows.
- Use normalize_html_entities() directly for output values.
- Use one readable query when multiple displays come from the same source and context.
- Do not merge components that serve different modals or unrelated contexts.
- Do not include components directly from main.php unless explicitly approved.
- Files inside components/ should normally be loaded through JavaScript AJAX into a container.

Inline event cleanup:

Avoid this:

```php
<button onclick="open_module_edit(<?php echo $recordID; ?>)" type="button">
```

Use this:

```php
<button
    class="btn-edit-module"
    data-record-id="<?php echo $recordID; ?>"
    type="button"
>
    Edit
</button>
```

Then bind it in JavaScript:

```javascript
bindEvent('click.moduleEdit', '.btn-edit-module', function () {
    open_module_edit($(this).data('record-id'));
});
```

==============================================================================
13. JAVASCRIPT FILE STRUCTURE
==============================================================================

JavaScript module files must follow this order:

```javascript
//===================================================================================================
// MODULE VARIABLES
//===================================================================================================

//===================================================================================================
// BIND EVENTS
//===================================================================================================

//===================================================================================================
// SHARED FUNCTIONS
//===================================================================================================

//===================================================================================================
// ALL FUNCTIONS RELATED TO TASK/MODULES
//===================================================================================================
```

Structure rules:
- Only small module state belongs under Module Variables.
- All event bindings must be grouped under Bind Events near the top.
- Event bindings must appear before main function implementations whenever practical.
- Shared functions must still belong to the current module.
- Registry/entity CRUD functions must be under All Functions Related To Task/Modules.
- Group functions by registry/entity/sub-module.
- Keep parent/master functions separate from child/detail functions.
- Do not scatter event bindings, helpers, and CRUD functions across the file.
- Do not create unrelated global helpers inside a module script.
- Optional IIFE is allowed only when the module needs variable isolation.

Module variable rules:
- Keep state minimal.
- Store add/edit state on the form using operation and recID attributes.
- Do not use localStorage for record IDs, selected record IDs, control numbers, or small action values.
- Use data-* attributes for small record-control values tied to buttons or rows.
- Do not store complete database records or large data inside HTML data-* attributes.

Example:

```javascript
var expenseclass_routes = {
    summary: 'expenseclass_summary',
    save: 'save_expenseclass',
    update: 'update_expenseclass',
    delete: 'delete_expenseclass'
};

var expenseclass_record_id = '';
```

==============================================================================
14. BIND EVENT RULES
==============================================================================

Use bindEvent() for JavaScript events.

Current Limitless pattern:

```javascript
bindEvent(event, selector, callback);
```

Example:

```javascript
bindEvent('click.expenseclassAdd', '#btnAddExpenseClass', function () {
    expenseclass_open_add_modal();
});
```

Rules:
- Do not create custom bind-event wrapper functions.
- Do not use inline JavaScript event attributes in PHP/HTML.
- Do not use addEventListener() for normal module events.
- Avoid manual .off().on() rebinding when bindEvent() is available.
- Use standard function syntax.
- Do not use arrow functions for project module scripts.
- Event handlers should be short.
- Event handlers should call a clearly named module function.
- Do not place large business logic directly inside bindEvent().
- Use event namespaces such as click.moduleAction and submit.moduleForm.
- bindEvent() supports dynamically loaded component content through delegated events.
- bindEvent() prevents duplicate event bindings.
- bindEvent() supports single selectors, comma-separated selectors, and selector arrays.
- For submit events, bindEvent() automatically prevents default browser form submission.
- For keypress/search events, check the key before running the function.
- In a bindEvent() callback, this refers to the matched element.

Banned inline HTML attributes:
- onclick
- onsubmit
- onchange
- onkeyup
- onkeydown
- onkeypress
- oninput
- onfocus
- onblur

Bind Event pattern:

```javascript
$(document).ready(function () {
    module_summary();

    bindEvent('click.moduleAdd', '#btnOpenModuleAdd', function () {
        module_open_add_modal();
    });

    bindEvent('submit.moduleForm', '#frmModule', function () {
        if ($('#frmModule').attr('operation') == 0) {
            module_confirm(0, 'save');
        } else {
            module_confirm($('#frmModule').attr('recID'), 'update');
        }
    });

    bindEvent('keypress.moduleSearch', '#moduleSearch', function (event) {
        if (event.which === 13) {
            module_summary();
        }
    });
});
```

==============================================================================
15. AJAX, RESPONSE HANDLER, AND LOADER RULES
==============================================================================

AJAX rules:
- Use jQuery AJAX.
- Use POST for CRUD and component refreshes unless the route/script loading flow requires GET.
- Use handleAjaxResponse() inside the AJAX .done() callback.
- Use handleAjaxError directly in the AJAX .fail() callback.
- handleAjaxResponse() accepts JSON text or an already parsed JSON object.
- The success callback runs only when response status is success.
- Use supported action types such as save, update, delete, post, send, approve, reject, and select.
- Use action type select when success toast should be suppressed.
- Pass a modal selector only when the documented handler should hide that modal on warning/error/invalid JSON.
- Reload server-rendered components after CRUD.

Standard JSON AJAX:

```javascript
function module_save() {
    startProcessLoader();

    $.ajax({
        url: '/router/?route=save_module',
        type: 'POST',
        data: $('#frmModule').serialize(),
        dataType: 'json'
    }).done(function (response) {
        handleAjaxResponse(response, function () {
            module_summary();
            $('#moduleModal').modal('hide');
        }, 'save');
    }).fail(handleAjaxError);
}
```

FormData AJAX:

```javascript
function module_save_with_file() {
    var formData = new FormData(document.getElementById('frmModule'));

    startProcessLoader();

    $.ajax({
        url: '/router/?route=save_module',
        type: 'POST',
        data: formData,
        processData: false,
        contentType: false,
        dataType: 'json'
    }).done(function (response) {
        handleAjaxResponse(response, function () {
            module_summary();
            $('#moduleModal').modal('hide');
        }, 'save');
    }).fail(handleAjaxError);
}
```

Loader rules:
- Use loading() for component/container loading.
- Use startProcessLoader() and endProcessLoader() for blocking save/update/delete actions.
- Do not use startProcessLoader() for normal component refresh.
- Do not refresh the whole page shell just to reload a summary.
- When searching while typing is explicitly approved, keep the search input outside the refreshed container so focus is not lost.
- Keep loading text simple.

Component loading:

```javascript
function module_summary() {
    $('#moduleSummaryContainer').html(loading('Loading...'));

    $.post('/router/?route=module_summary', {
        search: $('#moduleSearch').val() || ''
    }, function (html) {
        $('#moduleSummaryContainer').html(html);
    }).fail(handleAjaxError);
}
```

==============================================================================
16. CONFIRMATION RULES
==============================================================================

Use the global showConfirm() helper.

Rules:
- Do not create custom confirmation modals inside components.
- Keep showConfirm() generic and reusable.
- Do not add module-specific conditions, document types, or business logic directly inside showConfirm().
- Use one module-specific confirmation wrapper function.
- Place the confirmation wrapper under Shared Functions.
- The wrapper decides title, message, danger setting, and onConfirm callback.
- The callback calls the actual module task function.

Example:

```javascript
function module_confirm(confirmValue, condition) {
    if (condition === 'save') {
        showConfirm({
            danger: false,
            title: 'Save Record',
            msg: 'Do you want to save this record?',
            onConfirm: function () {
                module_save();
            }
        });
    }

    if (condition === 'update') {
        showConfirm({
            danger: false,
            title: 'Update Record',
            msg: 'Do you want to update this record?',
            onConfirm: function () {
                module_update();
            }
        });
    }

    if (condition === 'delete') {
        showConfirm({
            danger: true,
            title: 'Delete Record',
            msg: 'Do you want to delete this record?',
            onConfirm: function () {
                module_delete(confirmValue);
            }
        });
    }
}
```

17. MODAL, OFFCANVAS, AND BUTTON RULES
==============================================================================

Use static Bootstrap modals/offcanvas containers for forms.

Modal:

```html
<div
    class="modal fade"
    id="moduleModal"
    tabindex="-1"
    aria-hidden="true"
    data-bs-backdrop="static"
    data-bs-keyboard="false"
>
```

Offcanvas:

```html
<div
    class="offcanvas offcanvas-end"
    id="moduleEntry"
    tabindex="-1"
    data-bs-backdrop="static"
    data-bs-keyboard="false"
>
```

Rules:
- Static modal markup belongs in main.php unless explicitly approved otherwise.
- If a form component is AJAX-loaded, main.php should keep only the approved placeholder container.
- Submit buttons must use type="submit".
- Cancel/close buttons must use type="button".
- Buttons must use class/id selectors plus bindEvent().
- Do not use onclick, onchange, onsubmit, or other inline event attributes.
- Open modal JS should only reset/fill fields and show the modal.
- Use operation and recID attributes on forms for add/edit mode.
- Use HTML required, min, max, and maxlength attributes for UI guidance, but keep backend validation as final guard.

==============================================================================
18. HTML-IN-JS RULES
==============================================================================

Never build major HTML layout inside JavaScript.

Do not build these in JS:
- table rows
- table cells
- cards
- grids
- modal bodies
- full form sections
- attachment viewers
- repeated database display layouts

Allowed in JS:
- Set text on existing elements.
- Set values on existing inputs.
- Set HTML from a server-rendered component response.
- Toggle classes and attributes.
- Show/hide modals or offcanvas panels.
- Inject loading placeholders.
- Populate select/datalist option elements when returned by a component.
- Minimal local file preview UI when using the documented upload helper.

Design rule:
- If a UI layout changes, developers should check main.php and components/.
- They should not need to search through JS for hidden table/card/modal HTML.

==============================================================================
19. ROUTER RULES
==============================================================================

Use the E2E router pattern when the module/system supports routed file access.

Rules:
- Create or update route.php inside the module/task folder.
- Use unique snake_case route names with a module/task prefix.
- Keep route.php as a route map only.
- Do not put business logic in route.php.
- Do not put database queries in route.php.
- Always include the config block with the module rbac_route.
- Components/actions are normally called using POST.
- JS files are normally loaded using GET through script src.
- The methods key is optional when the active router supports route-new.php behavior.
- If methods are used, keep them accurate.
- Direct paths are allowed only when the module/system standard or a senior instruction approves it.

Required router config pattern:

```php
<?php

return [
    'config' => [
        'rbac_route' => '/global-settings/vendor-list/'
    ],

    'vendor_list_summary' => [
        'file' => __DIR__ . '/components/vendor_list_summary.php'
    ],
    'vendor_list_script' => [
        'file' => __DIR__ . '/script/vendor_list_script.js'
    ],
    'save_vendor_list' => [
        'file' => __DIR__ . '/actions/save_vendor_list.php'
    ]
];
```

Component route call:

```javascript
$.post('/router/?route=vendor_list_summary', {
    search: $('#vendorSearch').val() || ''
}, function (html) {
    $('#vendorListBody').html(html);
}).fail(handleAjaxError);
```

Script import:

```php
<script
    defer
    src="/router/?route=vendor_list_script&v=<?php echo (new DateTime())->format('YmdHis'); ?>"
></script>
```

Script versioning rule:
- Use DateTime for JS cache busting during active development.
- Do not use filemtime() for module script versioning unless a senior approves it for that module.

Preferred:

```php
<?php echo (new DateTime())->format('YmdHis'); ?>
```

Avoid:

```php
<?php echo filemtime(__DIR__ . '/script/module_script.js'); ?>
```

- Text search fields should fire on Enter key only.
- Filter dropdowns may fire on change.

Enter search:

bindEvent('keypress.moduleSearch', '#moduleSearch', function (event) {

Automatic typing search:
- Allowed only when explicitly requested for that module.

- Do not refresh the search input container.
- Do not refresh details automatically unless the user clicks a record or the task specifically requires it.

==============================================================================
23. API MODULE RULES
==============================================================================

API modules are different from normal registry modules.

Allowed API module structure:
- api_config/
- actions/
- shared/
- logs/ only for temporary diagnostics
- endpoint wrapper file in the module root

api_config/
- Endpoint URLs.
- API tokens.
- Table/column mappings.
- Timeout settings.
- Keep environment secrets out of shared code when possible.

shared/
- Reusable API utilities only.
- HTTP client wrappers.
- Token validators.
- Data normalization helpers.
- No direct request handling.

actions/
- Focused request handlers.
- One action per request type when possible.
- Validate token/session based on the API flow.
- Return JSON using json_msg_response().

endpoint wrapper files:
- Thin front controllers.
- Validate headers/token.
- Dispatch to the correct action.

API rules:
- Prefer token-based server-to-server endpoints.
- Include check_session.php only when a user session is required.
- Avoid SELECT *.
- Return only required columns.
- Remove request/response debug logs after debugging.

==============================================================================
24. FINAL HANDOFF CHECKLIST
==============================================================================

Before handing off:

- Run PHP syntax checks for changed PHP files.
- Run JS syntax checks when possible.
- Search for error_log().
- Search for console.log().
- Search for var_dump(), print_r(), and die().
- Search for temporary debug files/text.
- Confirm no short echo tags are used.
- Confirm no alternative PHP colon syntax is used.
- Confirm incoming request values use sanitize_input().
- Confirm output values use normalize_html_entities() directly.
- Confirm no one-use wrapper helper was created.
- Confirm CRUD responses use json_msg_response().
- Confirm caught exceptions use exception_handler($e, $conn).
- Confirm write actions use transactions.
- Confirm auditTrail() is after commit.
- Confirm delete actions fetch the old record before deleting.
- Confirm duplicate checks use SELECT 1 ... LIMIT 1 unless an actual count is needed.
- Confirm CRUD and component refreshes use POST unless explicitly approved otherwise.
- Confirm no unnecessary COUNT(*) is used.
- Confirm no SELECT * is used.
- Confirm no fetchAll() is used.
- Confirm direct DB display uses while loops.
- Confirm foreach is used only for non-database arrays or justified grouped/static data.
- Confirm repeated same-structure SQL is prepared once when run multiple times.
- Confirm component loading is server-rendered.
- Confirm no large HTML layout was added to JS.
- Confirm there are no inline JavaScript event attributes in PHP/HTML.
- Confirm module scripts use bindEvent().
- Confirm module scripts do not use arrow functions unless explicitly approved.
- Confirm record-control values use data-* attributes instead of localStorage.
- Confirm all JS event bindings are under the Bind Events section.
- Confirm shared JS helpers are under Shared Functions and are module-specific.
- Confirm CRUD JS functions are grouped by registry/entity/sub-module.
- Confirm JS functions, variables, selectors, and IDs use clear module ownership names.
- Confirm router files include the config rbac_route block.
- Confirm script versioning uses DateTime format during active development.
- Confirm existing behavior, selectors, routes, and backend calls were preserved unless the task required changes.
